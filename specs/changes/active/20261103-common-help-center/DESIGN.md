# 设计：按宿主装配的前端静态内容

第 1 至 7 节记录 2026-11-06 已验收的静态交付基线。平台资源访问控制以第 8 节的后续规划为准。

## 1. 数据归属

- `plugins/help/src/content/common/`：两端一致的通用说明，无端专属信息。
- `apps/admin/src/help/`：租户专属Markdown、图片及元数据，私有动态入口content.ts。
- `apps/admin-platform/src/help/`：平台专属资料及私有动态入口。
- 各宿主调用createHelpPlugin时传固定entry及loadContent，动态导入本宿主内容。共享插件不导入任一专属内容，也不使用扫描整个仓库内容的glob。

Markdown正文通过现有Vite `?raw` 导入，图片通过 `?url&no-inline` 生成本宿主带hash的静态资源；不将帮助内容放入跨端共用public目录。不需要任何专门构建task或代码生成步骤。

## 2. 内容提供器

HelpContentProvider提供固定domain及目录/文章/搜索/图片读取方法，均异步返回，阅读层不关心来源。当前由createStaticHelpProvider组合common和宿主定义，建立本域索引并解析稳定章节、阅读时长、前后篇和页面绑定；仅校验必要的同域引用、章节及图片闭包。

元数据和正文是普通源码；版本是前端发布标识，不再使用服务端SHA pin或409重试。将来后台维护需另行设计，替换loadContent/provider实现即可，不约定尚未确定的HTTP协议。

## 3. 本地搜索

直接使用本域内容，NFKC/大小写归一、空白分词AND；标题/关键词/章节/正文分别12/8/4/1，完整标题相等加20、包含加10。按分数、更新时间、稳定ID排序；分类先限制子树，再计数分页，默认20、最大50。高亮返回纯文本片段，最多160字符摘要，不将搜索文本当HTML执行。

## 4. 阅读运行态

保留当前布局、四类路由、Markdown净化、分类树、大纲、搜索分页和公共导航契约。loadContent只在有效当前端身份且不需改密时调用；运行态按身份纪元清理目录、位置和Query，异步返回再次核对身份。图片URL来自当前提供器的显式资产表；离开文章/换身份使旧图加载结果失效，组件清空src。

静态图片无需Base64传输、Blob URL、图片API或自建并发控制。缩略图仍在视口附近读取，原图打开预览时读取；利用浏览器原生资源缓存。搜索页沿用既有分页/Query组件，本地取数不新增服务调用。

业务页说明链接和已授权菜单viewPath匹配继续保留；core基础导航由common再导出，避免插件互依赖。无菜单的有效成员仍可读帮助，强制改密不例外。

## 5. 隔离与边界

分端依赖图与实际产物都必须验证。tenant 只含 common+tenant，platform 只含 common+platform，禁止运行时切换提供器。已验收版本的守卫覆盖阅读路由，静态文件的服务端访问控制列入第 8 节。

## 6. 后端与兼容

移除本次新增IAM help Java代码、错误码、Gradle声明和Python工具。原后端change记录为cancelled并归档，不删除历史规格。无DB/菜单种子/认证策略变更。已有页面入口继续使用相同文章ID，前端发布后不再依赖IAM版本。

## 7. 验证与收尾

已测试本地提供器、检索、分页、高亮、章节和图引用、身份变化及改密清理，并扫描两端真实制品。受控浏览器夹具覆盖已交付的阅读流程。真实账号和截图按剩余任务后补。

## 8. 平台静态资源访问控制规划

状态为待实施。保护单位是平台帮助资源目录，验收仍以各次资源请求的服务端判定为准。

### 8.1 构建与文件路径

- 前端仍维护 Markdown、元数据和图片。由现有 Vite 构建输出按版本区分的平台帮助数据和图像制品，拟通过同源 `/help-assets/platform/<version>/…` 提供。内容数据包含正文、目录、关键词及必要元数据，阅读器继续在本地建立索引。
- 平台受保护制品独立于公开站点根目录。平台专属正文、目录、搜索数据、原图和缩略图全部纳入保护。构建扫描同时覆盖入口和懒加载 JS、预加载依赖、公开静态文件、源码映射及租户制品，防止同一资料存在公开副本。
- 保留帮助路由、文章 ID、章节锚点和现有提供器边界。受保护资源版本与同次前端发布匹配。

### 8.2 复用现有会话鉴权

- 平台 Nginx 对资源 GET/HEAD 使用 `auth_request`。内部子请求通过可信平台 Host（含注册端口）走 Gateway 的现有 IAM 本人资料路由 `/iam/v1/me/profile`，外部 API 路径为 `/api/iam/v1/me/profile`。Nginx 只使用子请求状态，个人资料响应体不参与文件响应。部署前验证实际 Nginx 镜像包含该模块。[Nginx 模块文档](https://nginx.org/en/docs/http/ngx_http_auth_request_module.html)
- 子请求仅转交校验所需的 Cookie、设备指纹和可信来源信息，清除外来 Bearer、租户选择及应用身份头。平台 Host 来自部署配置或精确允许列表。Gateway 通过平台 Cookie 校验当前会话、代次、sid 和设备指纹，再由 IAM 核对当前成员及强制改密状态。两端 Cookie 可同时存在时仍以实际平台会话为准，并拒绝来自租户 origin 的嵌入式读取。
- 仅 2xx 校验结果允许读取文件。401/403 拒绝，鉴权超时、依赖故障或意外状态按服务端错误失败关闭。路径限制在当前发布的受保护目录内，未知文件返回 404。覆盖路径变体、Range、条件请求和 SPA 回退，避免资源改走公开处理路径。

### 8.3 前端读取与身份变化

- 平台通过同源请求复用现有设备指纹头与身份纪元处理，获取静态数据和图像字节。生产默认 DEVICE 模式，平台图片由帮助页按需请求，使用临时 Blob URL 显示和预览。退出、改密或身份变化时取消旧请求、清理目录和索引并释放 Blob URL。
- 文章链接继续指向帮助路由，接收者使用自己的平台会话阅读。原图、缩略图及正文资源 URL 单独访问时仍经过上述服务端校验。已验收的图文排版、懒加载和放大交互列入定向回归。

### 8.4 发布、缓存和回滚

- 双域名、IP 双端口和平台容器部署统一启用该规则。受保护响应及鉴权结果不走共享缓存，资源响应发送 `Cache-Control: private, no-store`。源站和容器仅从受控入口访问。
- 同批发布前端与对应 Nginx 规则，检查旧公开 hash、历史版本目录及 CDN 副本已撤下或受同等保护。回滚使用受保护版本及其匹配配置，或暂时关闭平台帮助资源入口。已交付到客户端的副本不具备远程撤回能力。
- 先用受控会话对真实 Nginx → Gateway → IAM 链路验收，记录正常读取、跨端直链、失效状态、旧资源及配置错误场景。真实业务账号实操与截图单独留证。

# 故障转移安全一致性评审稿

> 状态：approved（2026-11-13用户批准持久化账本与一次性重新登录）。来源：三 VM、六节点 Redis Cluster 的真实失败验收；完整施工依据见 DESIGN.md / phases/LEDGER-PHASES.md。

## 必须解决的问题

已确认的切换和退出写入在副本提升后回滚，使同一操作再次签发、旧 Cookie/事务/RT 重新有效。原截止保持不变，但不足以满足已批准的安全契约。

失败证据：[验收报告](CLUSTER-ACCEPTANCE.md)、[逐请求与复制证据](CLUSTER-ACCEPTANCE-20261113.json)。目前没有业务代码修复；不能用上轮 288 项单库回归通过来覆盖此失败。

## 推荐评审方向：可持久化、不可回滚的安全权威账本

1. 把会话有效性/撤销、绑定当前代次、切换幂等操作及已交付结果的事实，迁至满足已确认提交不丢失要求的事务存储；Redis 作为派生状态。该存储自身的故障转移也必须满足所需一致性，不能重现同一种异步回滚。
2. 以唯一操作 ID + 请求摘要 + 来源代次做事务比较与条件提交。正式结果先持久化再返回；节点重启只能读取同一结果，不能因 Redis 幂等键丢失而重新签发可用凭据。未提交的计算/签发结果不得获得有效身份。
3. 注销/撤销成功的返回条件是持久撤销事实已提交。BFF、Auth、Gateway/资源服务器和 RT 刷新都必须在建立身份前校验这一事实；权威源不可用返回 503，不以旧 Redis 或 LKG 放行。
4. 保留不可延长的原绝对截止，写入权威会话与操作记录；所有 token、Cookie、派生 Redis TTL 和后续 refresh 从该截止截断。恢复接口同时核对持久当前代次和撤销状态。
5. 缓存失效与远端撤销使用可靠 outbox/补偿；Redis 旧副本即使恢复旧会话，也只可作为待重建数据，不能恢复身份。返回给浏览器的 Cookie/公开 contextVersion 可维持现有契约，凭证结果必须按现有加密与脱敏要求保存。

影响范围：安全持久化表/迁移、Auth/BFF/Gateway/资源服务器认证链、结果恢复、清理、观测及协调发布。需要调整已批准的“无需数据库迁移”和纯 Redis 安全事实模型；详细模型、索引、事务边界、吞吐预算与迁移/回滚门禁需在实施前形成可执行设计。

## 可讨论的受限运行边界

若短期不接受持久化设计变更，只能明确限制运行模式：故障转移前停止接入、隔离旧主、失效全部相关身份并重新登录，再受控恢复。此方向牺牲可用性和无感恢复；不能把它描述为已满足自动、无感、任意网络分区下的三项安全保证。仅增加 WAIT、调整超时或继续叠加 Lua，必须通过同样的回滚反例后才能认定有效，不能直接替代一致性论证。

## 实施前需确认

- 接受新增事务安全账本和相应迁移，或明确受限运行模式；不得默认修改既定无迁移约束。
- 允许的故障模型、权威存储的确认提交保证、依赖故障时的 503/重新登录体验，以及认证热路径性能预算。
- 来源代次提交、并发刷新/撤销、丢回复、进程重启、Redis 重建、跨槽/跨节点补偿的原子边界与验收用例。

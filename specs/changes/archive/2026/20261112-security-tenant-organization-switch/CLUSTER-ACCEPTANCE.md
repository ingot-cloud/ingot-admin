# 跨 VM 网络分区与 Redis Cluster 验收（2026-11-13）

**结论：验收未通过，阻断发布。** 五组实际执行完成，三组通过、两组失败。原登录截止没有延长；复制回滚导致同一事务重复签发，并使已退出的 Cookie、已撤销 RT 重新有效。本轮未改生产代码、未提交；当前状态保持 validating，V02/C01 不关闭。

## 实测矩阵

| 场景 | 截止 | 幂等/会话结果 | 验收 |
|---|---|---|---|
| worker1 应用→集群 TCP 分区 | 保持 | BFF 查询/创建/提交均 503，直接 Auth 查询/签发均 503；Auth1 健康，原 Cookie/sid 不变；恢复后原事务签发一次 | 通过 |
| 完整复制后主节点依次故障 | 保持 | 实际自动选主，丢回复的事务从另一 BFF 恢复原结果；重复提交不再次签发 | 通过 |
| 已确认切换，复制落后后选主 | 保持 | 切换后旧 Cookie 原为 401；选主后变成 200。同一事务重试产生第二次签发，token 摘要不同 | **失败** |
| 已确认退出/撤销，复制落后后选主 | 保持 | 退出后旧 Cookie=401、旧 RT=400；选主后 Cookie=200、resume=200 且设置 Cookie、旧 RT=200 | **失败** |
| 拓扑变化后的原截止自然到达 | 不越界 | 按原 BFF 120 秒期限等待，显式重放 Cookie=401、最新 RT=400 | 通过 |

两个失败场景各记录了 40、43 个真实复制数据丢包；选主后的 cluster_current_epoch 分别为 10、13。同一失败事务的 operationId 和预分配 sid 摘要保持一致，但两次 token 摘要不同，不能将其当作“同一结果的重发”。

## 复现关键步骤

健康场景先在每个主节点同一连接执行标记 SET + WAIT，确认已有安全状态复制到副本。随后关闭主节点进程，依靠正常的集群多数投票自动提升副本，再检查结果和 Cookie。

回滚场景在健康复制基线之后，阻断三个副本接收主节点数据的 TCP 流量，保持投票链路。然后真实完成组织切换，或完成退出与 RT 撤销，取得 HTTP 成功并在旧主上确认旧身份已被拒绝。再依次杀掉三个当前主节点，等待真实自动选主。落后副本成为权威主节点后，前述拒绝结果变成成功。

未使用 FORCE/TAKEOVER，也未手工修改/恢复会话键、伪造业务响应。仅在服务环境启动前清空过本轮独占新集群，丢弃启动失败的夹具数据；验收期间的回滚来自复制丢包及自动选主。

## 原因与不能提前下的结论

BFF 的绑定代次、正式会话、事务阶段和清理任务，以及 Auth 的幂等键、授权和在线/撤销状态都依赖可回滚的 Redis 数据。副本恢复了较早的“合法状态”后，当前 token 重验仍会读到这个较早状态，无法知道“之前已经切换/退出”。同槽 Lua 保证单主执行原子性，无法阻止这些已确认写入在副本提升时丢失。

Redis 官方明确描述异步复制下已确认写入仍可能在故障转移时丢失；本轮结果是对该风险在实际组织会话链路上的验证，而非仅凭文档推断。[Redis Cluster 写安全说明](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/#write-safety)

“原截止不延长”只满足一项不变量，不能弥补重复签发和退出复活。不得用更长超时、只看选主成功、只重验 JWT，或把回滚后的 Redis 再称为“权威在线态”，将本轮改标为通过。
